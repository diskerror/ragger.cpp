# sqlite_backend.cpp Split Report

Generated by inspection only — **no code was changed**. This is a proposal
for how to break `src/sqlite_backend.cpp` (4,925 lines) and
`include/sqlite_backend.h` (228 lines) into smaller, logically cohesive
translation units.

## Current shape

- `include/sqlite_backend.h` — public `SqliteBackend` class declaration
  (pimpl pattern: one opaque `Impl` pointer, ~90 public methods).
- `src/sqlite_backend.cpp` — everything lives in one file:
  - Lines 1–115: free helper functions/anonymous namespace (`tags_from_metadata`, etc.)
  - Lines 118–4467: `struct SqliteBackend::Impl` — the entire implementation,
    ~4,350 lines, one giant struct.
  - Lines 4470–4925: `SqliteBackend::*` thin wrapper methods that just
    lock the mutex and forward to `pImpl->...()`. Mechanical, low-risk.

The `Impl` struct is the real problem: it mixes schema DDL/migrations,
CRUD for half a dozen tables, in-memory embedding caches, FTS-backed
search, and admin/auth concerns in one 4,300-line block with no
sub-namespacing.

## Why split by Impl's internal sections, not arbitrarily

`Impl` is one class, so a naive split can't just cut lines — it requires
turning `Impl` into a class with member functions defined **across
multiple .cpp files** (all `Impl::method_name` definitions, same header
declaration in `sqlite_backend_impl.h`). This is mechanical and safe
(pure code motion, no logic changes) as long as each new .cpp
`#include`s the shared private `Impl` declaration and any table/column
constants. Grouping below follows the natural seams already visible in
the code (migration order, comment banners, and cache-invalidation
groupings).

## Proposed files

1. **`sqlite_backend_impl.h`** (new, private header, not installed)
   - The `struct SqliteBackend::Impl { ... };` **declaration only** — every
     member and method signature that's currently implemented inline.
     Pulling declarations out of the .cpp is what makes multi-file `Impl::`
     definitions possible in the first place.
   - Included only by the new `sqlite_backend_*.cpp` files below.

2. **`sqlite_backend_schema.cpp`** (~1,300 lines: current 118–1654)
   - Constructor(s) (`Impl(Embedder&, path)`, DB-only ctor), `exec()`
     overloads, `column_exists`, `table_exists`, `create_schema()`,
     `db_version()`/`set_db_version()`, `migration_pending()`,
     `maybe_backup_before_migration()`, `reopen_db()`,
     `run_pending_migrations()`, `migrate_0_12_to_0_15()`,
     `migrate_documents_normalize()`, `pragma_bool()`,
     `rebuild_table_column_order()`, `migrate_0_15_to_0_16()`,
     `create_terms_schema()`.
   - Rationale: this is the largest coherent block — DDL and every
     versioned in-place migration. It's touched together whenever the
     schema changes and almost never touched alongside search/CRUD code.

3. **`sqlite_backend_admin.cpp`** (~280 lines: current 1662–1938)
   - `create_user_schema()`, user CRUD (`get_user_by_username`,
     `get_user_password`, `set_user_password`, `create_user`,
     `delete_user`, `update_user_token`, `get_user_by_token_hash`),
     settings (`get_setting`/`set_setting`), `list_schema_objects()`,
     `table_column_names`, `iterate_table_rows`, `create_views()`.
   - Rationale: auth/users/settings/schema-introspection is a distinct
     concern from memory-table CRUD, already visually grouped in the
     source (comment banners at 4859/4907 in the current file confirm
     the seam continues into the public wrapper section too).

4. **`sqlite_backend_cache.cpp`** (~350 lines: current 1938–2366 minus
   embedding helpers, plus `bind_embedding`/`bind_embedding_version`
   from lines 136–230 and `decode_embedding`-style helpers noted around
   line 2262)
   - `invalidate_cache/_doc/_dec/_turn`, `ensure_cache`,
     `ensure_doc_cache`, `ensure_dec_cache`, `ensure_turn_cache`,
     `resolve_epoch`, `bind_embedding`, `bind_embedding_version`.
   - Rationale: the four embedding caches (summaries/documents/decisions/
     turn_summaries) are a self-contained subsystem the header comments
     already describe as mirroring one another; isolating them makes the
     cache-invalidation contract auditable in one file.

5. **`sqlite_backend_write.cpp`** (~1,350 lines: current 2366–3654)
   - All the store/finalize/update mutators: `store_document`,
     `get_or_create_model`, `get_or_create_session`, `store_turn`,
     `finalize_turn`, `store_summary`, `store_decision`,
     `turn_summary_exists`, `reset_abandoned_turn_summaries`,
     `finalize_turn_summary`, `mark_turn_summarized`, `store_episode`,
     `set_summary_updated_at`, watermark get/set,
     `advance_session_boundary_watermark`,
     `advance_project_boundary_watermark`, `store_session_summary`,
     `store_project_summary`, `summary_exists_exact`,
     `decision_exists_exact`, `turn_exists_fuzzy`, `update_turn_meta`,
     `set_decision_status`, `update_summary_text`, `set_summary_tags`,
     `update_text`.
   - Rationale: this is every write path for turns/summaries/decisions/
     episodes — the largest single block after schema/migrations, but
     cleanly separable from search (read path) and from schema DDL.
     Still large (~1,350 lines); if it needs a further cut later, turns
     vs. summaries vs. decisions/episodes is the next natural seam.

6. **`sqlite_backend_search.cpp`** (~280 lines: current 3710–3989)
   - `search()`, `search_text_only()`.
   - Rationale: the FTS5 + vector blended ranking logic is the most
     algorithmically distinct piece of the file and the one most likely
     to be read/modified in isolation (scoring tweaks).

7. **`sqlite_backend_maintenance.cpp`** (~470 lines: current 3989–4459)
   - `count()`, `table_row_counts`, `count_embeddable_rows`,
     `has_embeddings`, `load_all`, `embed_tables`, `rebuild_embeddings`,
     `backfill_embeddings`, `embedder_usable`, `get_embedding_version`,
     `increment_embedding_version`, `reindex_table`,
     `update_document_embedding`, `update_decision_embedding`,
     `update_summary_embedding`, `update_turn_embedding`,
     `has_keep_tag`, `delete_memory`, `delete_batch`,
     `cleanup_old_conversations`, `close`.
   - Rationale: housekeeping/backfill/reindex/delete — operational
     concerns invoked by the daemon's housekeeping timer and CLI admin
     commands, not by normal read/write request handling.

8. **`sqlite_backend.cpp`** (kept, shrinks to ~120 lines: current
   1–115 free helpers + 4470–4925 public wrappers)
   - The small anonymous-namespace helpers (`tags_from_metadata`, etc.)
     that don't belong to `Impl`.
   - The `SqliteBackend::*` public methods, which are one-line
     `lock_guard` + forward-to-`pImpl` calls. These are mechanical and
     benefit from staying together as the class's single public-API
     surface — a reader scanning the real `sqlite_backend.cpp` should
     see the whole public contract at a glance.

## `include/sqlite_backend.h` (228 lines)

Left as-is. It's already just the public class declaration plus the
plain-data result structs (`SearchResult`, `TurnRecord`, etc.) it
returns — reasonably sized and not a maintenance pain point. Splitting
it further would mean separating those data structs into their own
header (e.g. `sqlite_backend_types.h`), which is optional polish, not a
necessity. Only worth doing if the split above is pursued and a new
`sqlite_backend_impl.h` needs `#include`s from it anyway.

## Suggested order of operations (when actually implementing)

1. Extract `struct SqliteBackend::Impl` member declarations into
   `sqlite_backend_impl.h` unchanged (pure declaration move).
2. Move method **bodies** out into the 6 new `.cpp` files above by pure
   cut-and-paste (`Impl::method(...) { ... }` unchanged), each file
   `#include`s `sqlite_backend_impl.h` + whatever headers it needs
   (sqlite3, nlohmann::json, etc.).
3. Update `CMakeLists.txt`'s source list.
4. Build once, fix only include-related compile errors (there will be
   some — helper functions currently visible via textual proximity in
   the single .cpp will need to move to a small shared internal header
   or be duplicated as `static` where trivial).
5. Run the existing `tests/test_sqlite_backend.cpp` suite unchanged to
   confirm behavior parity — this is a pure refactor, so all existing
   tests should pass without modification.
